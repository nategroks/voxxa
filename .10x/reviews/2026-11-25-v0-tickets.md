## #59: cause, fix and numbers (for the PR body)
**Cause.** whisper-rs-sys 0.11.1 builds whisper.cpp through the `cmake` crate 0.1.58 and always asks for the Release configuration (`whisper-rs-sys-0.11.1/build.rs:158`). On MSVC, when no CMake generator is named, the crate sets `CMAKE_C_FLAGS_RELEASE` and `CMAKE_CXX_FLAGS_RELEASE` itself, from the `cc` crate's flags minus every `-O` or `/O` word (`cmake-0.1.58/src/lib.rs:723-726`, `:752-767`). That replaces CMake's own `/MD /O2 /Ob2 /DNDEBUG`, so every Windows release build (the installers from `build.yml`, `npm run tauri build`, `cargo build --release`) compiled whisper.cpp without optimisation. The broken build's whisper-rs-sys `out/build/CMakeCache.txt` reads `CMAKE_C_FLAGS_RELEASE:STRING= -nologo -MD -Brepro -W0` (C++ the same).

Debug builds escape it. whisper-rs-sys sets `CMAKE_BUILD_TYPE=RelWithDebInfo` in a debug build (`build.rs:228-233`), so the crate's override lands on the RelWithDebInfo line, while the Visual Studio generator still builds `--config Release` with CMake's own `/O2` line. The override is MSVC-only, so Linux and macOS builds keep CMake's defaults (read in the crate's code; not measured).

**Fix.** whisper-rs-sys passes every `CMAKE_*` environment variable to CMake as a `-D` (`build.rs:235-243`), and the crate leaves a variable that is already defined alone. `build.yml`'s Windows job sets both variables to `-MD -O2 -Ob2 -DNDEBUG`: dashes, because the build step runs in Git Bash, which rewrites `/MD` as a path; that job only, because `-Ob2` breaks gcc and clang. The fixed cache reads `CMAKE_C_FLAGS_RELEASE:STRING=-MD -O2 -Ob2 -DNDEBUG`. Guards:
- A new Windows rust-cache key, `release-portable-ggml-o2`. whisper-rs-sys reruns its build only when `VULKAN_SDK`, `HIP_PATH`, `AMDGPU_TARGETS` or its `wrapper.h` change, so a restored unoptimised build would stay. rust-cache's restore key already includes a hash of every `CMAKE*` variable, so the new env alone drops the old cache; the new name makes that visible, and the test pins it.
- "Check that whisper.cpp was built with -O2" (`scripts/ci/check-msvc-release-flags.sh`), right after the installer build. It fails with `::error::` when no whisper-rs-sys `CMakeCache.txt` exists or when either flag line lacks `-O2`. Its test runs on every PR (`ci.yml`, `budgets` job).
- `tests/release_config.rs` pins the two lines to the Windows job's `env:`, the key, and the check step's place and form.

`ci.yml` and `full-eval.yml` are unchanged: they build debug only. For local builds, dot-source `scripts/dev/msvc-release-flags.ps1` and run `cargo clean --manifest-path src-tauri/Cargo.toml -p whisper-rs-sys --release` once (`docs/RELEASING.md` § 7). ADR-021 § 1 has the details.

**Numbers** (release `voxxad`, Whisper Tiny, 30 s encoder, a 2:00 private song, the booth PC, 2026-11-24/25): 461 s of compute broken, 130 s fixed (3.5 times faster).

**Still open after the merge.** `build.yml` runs only for a tag, so the next founder-approved rc draft's Windows job is the first real run of the check. It must pass and print two flag lines with `-O2`. The founder's own booth timing with the script (≤ 150 s) is a checklist item in `status.md`.

## V0-01 [low, tooling] The debug CMake cache's RelWithDebInfo flag lines have no /O2 (unused today)
**What.** In a debug build, whisper-rs-sys sets `CMAKE_BUILD_TYPE=RelWithDebInfo`, so the `cmake` crate writes `CMAKE_C_FLAGS_RELWITHDEBINFO:STRING= -nologo -MD -Brepro -W0` (C++: ` -DWHISPER_DEBUG -nologo -MD -Brepro -W0`), again without `/O2`. Today that line is not used: the Visual Studio generator builds `--config Release`, and a debug target folder's cache keeps `CMAKE_C_FLAGS_RELEASE:STRING=/MD /O2 /Ob2 /DNDEBUG` (Release `ggml.vcxproj`: `<Optimization>MaxSpeed`). `check-msvc-release-flags.sh` passes on such a folder.
**Where.** `whisper-rs-sys-0.11.1/build.rs:228-233`; `cmake-0.1.58/src/lib.rs:752-767`, `:879`. Seen in ten debug caches on the booth PC, 2026-11-25.
**Why.** It becomes the same defect if a Windows debug build ever uses a single-config generator (for example `CMAKE_GENERATOR=Ninja`), which builds `CMAKE_BUILD_TYPE` (RelWithDebInfo) with these flags. CI's debug timings and the replay gate would then slow down, and nothing would say why.
**Suggested fix.** No code change while the Visual Studio generator is used. If a single-config generator is adopted on Windows, set `CMAKE_C_FLAGS_RELWITHDEBINFO` and `CMAKE_CXX_FLAGS_RELWITHDEBINFO` the same Windows-only way and let the check read that line. Filing it is optional: it can instead be a line in ADR-021's review trigger.

## V0-02 [low, tooling, performance] Local release builds without the script are still unoptimised, and nothing warns
**What.** V0 protects only `build.yml`'s Windows job. A release build on a developer's or a church's own PC (`npm run tauri build`, `cargo build --release`, a release `voxxad` for timings) in a shell that did not dot-source `scripts/dev/msvc-release-flags.ps1` still compiles whisper.cpp without `/O2`, with no message. Running the check script by hand is the only way to know (`docs/RELEASING.md` § 7).
**Where.** `src-tauri/build.rs`; `scripts/dev/msvc-release-flags.ps1`; ADR-021 Consequences ("Local release builds still need the founder's shell script").
**Why.** Booth timings and local builds are what the founder trusts for the 95% and latency decisions. A slow local build looks like a slow model.
**Suggested fix.** In `src-tauri/build.rs`, when `PROFILE` is `release`, `CARGO_CFG_TARGET_ENV` is `msvc` and `CMAKE_C_FLAGS_RELEASE` has no `-O2` or `/O2` word, print `cargo:warning=whisper.cpp will be built without /O2 (#59): dot-source scripts/dev/msvc-release-flags.ps1 first`, with `cargo:rerun-if-env-changed` for both variables. The plan gave V0 "no Rust change", so this waits for a later step.

## V0-03 [low, tests, tooling] The macOS and Linux release builds' whisper.cpp flags are not checked
**What.** The `-O2` check runs in the Windows release job only. On gcc and clang the `cmake` crate does not override `CMAKE_*_FLAGS_RELEASE` (the override is under `generator.is_none() && msvc`, `cmake-0.1.58/src/lib.rs:752`), so CMake's own `-O3 -DNDEBUG` should apply. Nobody has read a macOS or Linux release CMake cache.
**Where.** `.github/workflows/build.yml`, job `build` (tauri-action); `scripts/ci/check-msvc-release-flags.sh` (it accepts only `-O2` or `/O2`).
**Why.** If a later crate version changed this, the macOS and Linux installers would get #59's slowness, and no gate would see it.
**Suggested fix.** Record one CMake cache flag line from each platform in the next rc run, or let the script also accept `-O3` and run it after tauri-action in the `build` job, pinned in `release_config.rs`.
