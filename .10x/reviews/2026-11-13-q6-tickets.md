## Q6-01 [medium, adr] The GUI stores the whole `SmartConfig`, so retuned `evidence` defaults never reach a user who has saved a setting
**What.** `saveSmartConfigSoon` (`src/main.js:1472-1492`) writes the whole `SmartConfig` to `localStorage` (`voxxa.smartConfig`). Since Q6 that includes the `evidence` block (ADR-016 Decision 7). On the next start, `loadSmartConfig` (`src/main.js:1421-1441`) lays the stored copy over `get_smart_config`'s defaults and pushes it back with `set_smart_config`. Once a user moves any of the four sliders, every later change to an `EvidenceConfig` default is ignored, without any message. The same is already true of the other fields the GUI does not show (`min_start_match`, `softmax_temperature` and the rest).
**Where.** `src/main.js:1421-1441` and `1472-1492`. ADR-016 Decision 7 and its second amendment, item 4.
**Why.** ADR-016's numbers were tuned on synthetic speech and must be re-tuned on real recordings (Q5-01, #73). A retune shipped in an update would not reach the churches that already use the app, and the live conductor would no longer match what CI measured.
**Suggested fix (a GUI change, so it needs the user's approval under Q6 user decision 5).** Store and restore only the four fields the GUI shows (`silence_to_blank_secs`, `unrecognized_speech_to_blank_secs`, `song_confidence_floor`, `min_song_dwell_secs`). On load, merge only those four from a stored object, so the backend defaults win for everything else, including `evidence`, and an old stored object with the whole config is cut down to the four fields. About 6 lines; GUI row 2,951 / 3,000. Test: a `gui_events`-style pure helper, or a note in the QA checklist.
**Update, 2026-11-18.** Still open and still needs the user's approval. One side effect is now contained: `Tracker::decide` clamps a stored `decay` to 0..=1 (587d2ad), so an out-of-range value from `localStorage` cannot break the accumulator. The priors and `threshold` are not range-checked.

## Q6-03 [medium, performance] p95 latency is 4.87 s, still about twice the 2.5 s budget
**What.** After ADR-016, the total p95 over 21 hits is 4,870 ms (5,850 ms on the five fixtures of the Q6 decision). Median 2,310 ms. That is stream time at file speed, so it leaves out inference; live it would be higher (Q4-02, #60). 7 of 21 hits are under 2 s, 10 are at 2.1-2.9 s and 4 are over 3 s:
- the first slide of a service, twice at 3,900 ms (the first transcript arrives at 6 s for a part that starts at 2.1 s);
- the second verse of the first hymn in `prayer-between-songs`, 4,870 ms: its first transcript opens every slide of that hymn, so the tracker waits for a second one;
- the return to verse 1 in `jump-be-thou-my-vision`, 5,850 ms: Whisper Tiny gives no transcript for 6 s, and then the 12-word window, heavy in function words, holds the current slide for one more transcript. The log's floor for that hit is 3,850 ms, so about 2 s is the conductor's.
**Where.** `src-tauri/src/aligner/evidence/mod.rs` (`score`, `Tracker::decide`); `src-tauri/src/transcription/recognizer.rs:61` (`MIN_WORDS = 4`, the stitcher's hold); `fixtures/recordings/*/truth.jsonl`.
**Why.** ADR-009's budget is p95 ≤ 2.5 s. The Q6 rule's latency limb still fails after the minimum; the false-advance limb is met.
**Suggested fix.** Measure live first: one `voxxad --realtime --shadow` run per fixture to get wall-clock latency (with Q4-02's hop cost). Then try each of these separately and measure it with `voxxa-eval`: a smaller stitcher hold for the first transcript after silence; weighting content words over function words in `tokens`/`score`; a lower threshold only for the "next" prior. Do not tune further on synthetic speech alone (Q5-01).
**Update, 2026-11-18.** Unchanged at the final head 97cc21b: p95 4,870 ms, median 2,310 ms over 21 hits. The ponytail re-run reached the jump row's floor (p95 3,850 ms) with a different score; trying that idea in base is Q6-15.

## Q6-06 [low, tooling] No importer writes section labels, so every GUI song is unlabelled
**What.** `sections[].kind` (ADR-016 Decision 1) is read from native setlists and `voxxad --setlist` files only. No importer writes it, and the GUI has no way to set it (user decision 5: no GUI change). In the GUI every song is unlabelled: no chorus prior, and every slide counts as a section start. A repeated chorus is still followed, but with less help.
**Where.** `src-tauri/src/importers/` and `src-tauri/src/planning_center/mod.rs` (the `Song` literals now set `sections: Vec::new()`); `docs/SETLIST_FORMATS.md`.
**Why.** The labels exist to help with repeated choruses and jumps; real setlists will not carry them.
**Suggested fix.** Map the labels the source formats already carry: OpenSong `[V1]`/`[C]`/`[B]`, ChordPro `{start_of_chorus}`, OpenLyrics `<verse name="c1">`. Test each importer on a public-domain example. Mind the importers row (1,386 / 1,600).

## Q6-08 [low, documentation] One Be Thou My Vision line's public-domain source is not cited

**Where.** `fixtures/recordings/jump-be-thou-my-vision/setlist.json` (song 0, slide 3; the generator reads its text from this file); `fixtures/SOURCES.md:15`.
**Why.** ADR-007 and the content rule allow only public-domain text. The risk is low, but it is unverified.
**Suggested fix.** Check that line against a pre-1929 hymnal scan (for example on hymnary.org) and cite it in `SOURCES.md`. If no pre-1929 print exists, use Hull's 1912 wording, regenerate the WAV with `scripts/fixtures/make_tts_fixture.ps1`, and re-record the log (`voxxa-eval --full --record`).

## Q6-12 [low, tooling] Every cargo build rewrites the generated schema files' line endings
**What.** With `core.autocrlf=true`, every `cargo build` rewrites `src-tauri/gen/schemas/desktop-schema.json` and `windows-schema.json` with different line endings. Git shows them as modified, with no content change. In Q6 the fixture audit, the finisher and a verifier each had to restore or skip them.
**Where.** `src-tauri/gen/schemas/`; `.gitattributes`.
**Why.** A careless `git add -A` would commit noise, and a "worktree clean" check fails after any build.
**Suggested fix.** Add `src-tauri/gen/schemas/*.json text eol=lf` (or `-text`) to `.gitattributes`, renormalise once, and check that a build leaves `git status` clean on Windows.
**Update, 2026-11-18.** Seen again by verifier B at 97cc21b: the only working-tree noise after its gates was this line-ending churn in `src-tauri/gen/schemas/*.json`.

## Q6-13 [low, tests] The tracker's own move clearing the operator's left slide is not pinned (verifier B, 97cc21b)
**What.** After a move it makes itself, `Tracker::decide` sets `self.left = None`, so the slide an operator left stops having prior 0 (ADR-016 Decision 6: "until the conductor next moves on its own"). Deleting that line passes every scripted test, the CI eval step and the full `cargo test`. Under the mutant the zero prior lasts until a transcript scores 0.5 or more on the current slide, which usually comes one transcript later, so the effect is small.
**Where.** `src-tauri/src/aligner/evidence/mod.rs:183` (`self.left = None;` after `self.at = Some((song_index, best));`); `src-tauri/tests/conductor_evidence.rs`.
**Why.** Decision 6 promises the left slide becomes an ordinary candidate after the tracker's next own move. A refactor could drop that without any gate noticing.
**Suggested fix.** A test with placeholder words: the operator steps back (so the left slide is the old one), the tracker then moves forward on its own, and the very next transcript sings the old left slide with words that score below 0.5 on the new current slide. Assert that the conductor may move there. Check that the mutant fails it.

## Q6-14 [low, tests] The tracker's bookkeeping after an operator move is only partly pinned (verifier B, 97cc21b)
**What.** Three lines in `moved_by_other` (called when a song start, `manual_step` or `jump_to_song` sets the position) can each be removed with no failing test, CI eval step or full `cargo test`:
- `self.entered(song, from, current)` (`:193`): after a `manual_step` from a verse into a chorus, the chorus end's "next" becomes the list-next slide instead of the slide after the verse that led in. That is Decision 2's repeat-aware prior after an operator override, and it is untested.
- `self.resume = None` (`:191`): a stale resume slide only matters on a song change while the old song is in a chorus and the new song starts on a chorus slide.
- the reset of the other slides' evidence to 0 (`:196`): mostly masked, because the left slide's prior of 0 and the decay keep the old slide below the current one on the first transcript.
**Where.** `src-tauri/src/aligner/evidence/mod.rs:189-201` (`moved_by_other`); `src-tauri/tests/conductor_evidence.rs`.
**Why.** "The operator always wins" is the conductor's most important promise. Its main paths are pinned (verifier B killed the "left never set", "left prior ignored", "left cleared at once" and "operator move not resetting the tracker" mutants), but these three lines are not.
**Suggested fix.** (1) A labelled song verse, chorus, verse, verse: sing slide 2, `manual_step(-1)` into the chorus, sing the chorus, then sing slide 3; assert a goto to 3 on the transcript that the `prior_next` arithmetic predicts (the `prior_section` path is slower). (2) A `Tracker`-level unit test that calls `decide` with a changed `current` and asserts the reset: a slide that had built up evidence does not move sooner after an operator step than from a fresh start. Low priority.

## Q6-15 [low, performance] Try the ponytail re-run's "tail of the current slide" context for slides being entered
**What.** The ponytail re-run (`q6/ponytail` @ 7d4b4b6, `src-tauri/src/aligner/evidence/mod.rs` there) scores any other slide against the current slide's last 12 tokens followed by that slide's first 24, and asks the best slide to lead every other slide by the margin. That builds up evidence for the next part while the current one ends. On the shared fixtures it is faster on one row: the jump's p95 is 3,850 ms (the floor the recorded log allows) against base's 5,850 ms. On the unlabelled refrain log it gives p95 3,900 ms, where base gives 5,310 ms.
**Where.** `src-tauri/src/aligner/evidence/mod.rs:80-92` (`score`, its `entering` term and `LEAD_SLACK`); compare `q6/ponytail:src-tauri/src/aligner/evidence/mod.rs` (`hop`, `LEAD` = 24).
**Why.** Base's score is an incremental share and works differently, so the comparator did not graft the idea: a swap could make `prayer-then-reprise` or `prayer-between-songs` worse. It is the one place where the re-run's mechanism beat base (`2026-11-13-ponytail-q6.md` §10.5). It may help Q6-03.
**Suggested fix.** Add the current slide's tail as context for the slide being entered in base's `score()`, as one change. Adopt it only if replay shows no fixture worse on any cell, and keep `false_advances` at 0 on the refrain and prayer fixtures. Do not tune on synthetic speech alone (Q5-01).
