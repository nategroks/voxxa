## Q10-01 [medium] Settings: `loadSettings` throws "settings is not defined", so the threshold and margin labels never update
**What.** `loadSettings()` in `src/main.js` reads `settings.similarity_threshold` and `settings.margin` (`src/main.js:1102-1111`), but no `settings` exists in that function or the module: it fetches only devices, models and the language (`:1052-1056`). The `ReferenceError: settings is not defined` is caught by the function's own `catch` and logged as "Failed to load settings". Everything after the first `settings.` read is skipped: the threshold and margin sliders keep the HTML defaults (70 and 10), their value labels are never set from the backend, and the `input` listeners that keep the labels in step are never added.
**Where.** `src/main.js:1050-1118` (`loadSettings`); `index.html:280-286`. The two reads date from 0a15de1 ("feat: rebuild app as worship slide auto-advancer"). Found by the ponytail lane in Q10; the 10x lane did not report it. The finisher saw it in the guarded real app at 0571ea6 (the labels stayed at 70% and 10), and verifier A saw the same console line (`src/main.js:1116`). It is not a CSP issue.
**Why.** An operator who moves either slider sees a stale number, and the sliders may not show the values the backend uses. It also writes an error to the console on every visit to Settings, which hides real errors during booth support.
**Suggested fix.** Fetch the settings the sliders show (the command that returns `similarity_threshold` and `margin`, if one exists; otherwise drop the two reads and keep the HTML defaults), add the two listeners outside the `try`, and add an e2e check that moving each slider updates its label and that the console has no `ReferenceError`.

## Q10-02 [medium] First run advanced to step 2 by itself in the guarded real app, saved an audio device and ran 12 discovery probes
**What.** In the ponytail lane's guarded real-app run (`com.voxxa.qa10p`, no microphone, driven only through CDP), on the first two launches the first-run flow moved from step 1 to step 2 with no scripted input, wrote `voxxa.audioDevice` to local storage, and ran 3 discovery rounds: 12 loopback probes to 127.0.0.1 ports 1025, 5506, 4316 and 8082. Nothing was clicked that should have done that. A later 20-second instrumented watch saw no input and no change, and a full rerun left the outbound counter at 12. The lane's best guess is outside input (someone at the booth PC, or another process sending input to the new foreground window), but it could not explain it.
**Where.** `src/simple/` first-run flow (ADR-017); the discovery module (`src-tauri/src/discovery/`). Ponytail lane, Q10. Not reproduced since: the base and verifier runs attached a CDP helper about 1 s after start, saw "Step 1 of 4" with no audio device and the focus on `BODY`, and pressed Skip setup.
**Why.** On the booth PC an unasked first-run step chooses an audio device for the operator and starts probing; if it happens when the window is shown, a church's first launch may skip the device choice. It matters for booth reliability, not only for tests.
**Suggested fix.** Reproduce on a clean scratch identifier (`com.voxxa.qaNN`, data folder deleted first), with CDP attached before the window is shown, and record every `click`/`keydown` event. Check first for a focused default button (`autofocus`, or focus moved in code) that gets activated when the window is shown or by a stray Enter/Space; then for a timer or an event that calls the step-1 "next" handler. Add an e2e check that the first-run flow stays on step 1, writes no `voxxa.audioDevice` and makes no discovery call until the operator acts.

## Q10-03 [low, security] Turn on `requireSignedVersion` once the Tauri CLI signs the version
**What.** `latest.json` is not signed; the minisign signature covers only the artifact. `requireSignedVersion` would bind the version to the signature, but the pinned `@tauri-apps/cli` 2.10.1 writes no `version:` into the trusted comment, so turning it on now would refuse every update.
**Where.** `src-tauri/tauri.conf.json` (`plugins.updater`); `package.json` (`@tauri-apps/cli`); ADR-020 § 3.
**Why.** Until then, whoever can write the repository's releases can offer an older, genuinely signed build under a higher number.
**Suggested fix.** Bump the CLI to a version that records the signed version, check one `.sig`'s trusted comment, and turn the option on in the same PR, with a `release_config.rs` assertion.

## Q10-04 [low, security] The NSIS installer's inner `voxxa.exe` is unsigned on the SignPath path
**What.** SignPath signs the built `-setup.exe` and `.msi`; the `voxxa.exe` inside the NSIS installer is not deep-signed. On the Azure path `signCommand` signs it during the build.
**Where.** `.github/workflows/build.yml` (Windows job); `packaging/signpath/artifact-configuration.xml`; ADR-020 Consequences.
**Why.** Windows shows the installed program as unsigned in some places (Defender, Task Manager) even when the installer was signed.
**Suggested fix.** Ask SignPath whether the artifact configuration can sign the main binary before NSIS packs it (a two-step signing request), or sign `voxxa.exe` first and bundle afterwards.

## Q10-08 [low, tests, security] Three release-workflow mutants survive `release_config.rs`
**What.** Verifier B (round 2, at f424c74) applied 30 mutants; 27 were killed. Three survived, none from the required list:
- a step that publishes the draft through the API (`gh api -X PATCH repos/$GITHUB_REPOSITORY/releases/<id> -F draft=false`) passes: `tag_builds_make_draft_releases_only` bans only the literal strings `releaseDraft: false` and `gh release edit`;
- a `pull_request` trigger added to `build.yml` passes. A PR from a fork gets no secrets, but a PR from a branch of this repository would reach the signing and updater secrets. Today `build.yml` has only `push: tags: v*` and `workflow_dispatch`, and `ci.yml` and `full-eval.yml` reference no `secrets.`;
- removing the `if:` from the SignPath step passes, because the test only checks that the string `if: steps.path.outputs.signing == 'signpath'` appears somewhere, and two other steps still carry it. Without SignPath secrets that step would run with an empty artifact id and fail the Windows build instead of skipping.
**Where.** `src-tauri/tests/release_config.rs:144` (`tag_builds_make_draft_releases_only`) and the SignPath checks; `.github/workflows/build.yml`.
**Why.** Each one breaks a founder decision (drafts only; signing lights up only when its secrets exist) or exposes the updater key, and no gate would notice.
**Suggested fix.** In `tag_builds_make_draft_releases_only`, also refuse `draft=false`, `draft: false`, `--draft=false` and any `gh api` call with `-X PATCH` on releases. Assert that the `on:` blocks of `build.yml` and `winget.yml` have no `pull_request` or `pull_request_target`, and that no `pull_request`-triggered workflow names a `secrets.` value other than `GITHUB_TOKEN`. Use the `step()` helper (`release_config.rs:210`) to assert that "Upload the unsigned installers for SignPath", "Sign with SignPath (approve the request in SignPath)" and "Use the signed installers" each carry the SignPath `if:`, and "Install trusted-signing-cli" the Azure one. Prove each with its mutant.

## Q10-09 [low, tooling, performance] Release binaries: decide the CPU baseline and check it; the portable-ggml comment is stale
**What.** Q10 gave the release builds the portable ggml build (`CMAKE_PROJECT_INCLUDE` → `src-tauri/cmake/ggml-portable.cmake`, `GGML_NATIVE` off), which closes #142's crash risk. Two parts of #142 were not done: the baseline decision (the portable default needs AVX, AVX2, FMA and F16C; pre-2013 CPUs would need `WHISPER_AVX2=OFF` and similar), and a check that the release binary contains no AVX-512 instructions. The file's own comment still says "CI only (ci.yml, full-eval.yml set CMAKE_PROJECT_INCLUDE to this file …)", but `build.yml:43` sets it too.
**Where.** `src-tauri/cmake/ggml-portable.cmake:1`; `.github/workflows/build.yml:40-43`; #142.
**Why.** A church PC older than about 2013 could still crash on load with no useful error, and the comment misleads anyone changing the release build.
**Suggested fix.** Founder decision on the baseline (AVX2 is likely fine for booth PCs bought since 2014). Fix the comment. Add a release-job step that disassembles the ggml objects or the built `voxxa.exe` and fails on AVX-512 opcodes, or record why it is not worth it.

## Q10-10 [low, tests] The strict CSP is proven only in WebView2
**What.** Zero CSP violations were shown in the mocked browser (headless Edge) and in the guarded real app on Windows (WebView2). Nobody ran the app under WKWebView (macOS) or WebKitGTK (Linux), whose CSP handling differs in details (for example `ipc:` and `http://ipc.localhost`, and how they report violations).
**Where.** `src-tauri/tauri.conf.json:49`; `scripts/qa/csp-real-app.mjs` (Windows only, CDP).
**Why.** The rc draft carries `.dmg`, `.AppImage` and `.deb` builds; a CSP break there would show as a blank or unstyled window, and no gate would see it.
**Suggested fix.** Before the full release, open the rc's macOS and Linux builds once (a test machine, never LHMEZPC01) and check the Web Inspector console for CSP reports on the main window, Simple mode, the stage window and Call for help. Record the result in the QA record. If either fails, fix the policy for all platforms together, with a `release_config.rs` assertion.
