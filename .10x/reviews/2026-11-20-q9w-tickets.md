## Q9W-01 [medium, tests] A step of several keys that stops halfway leaves Voxxa behind the screen, and the song's end can then get one Right too many
**What.** When the conductor jumps two or more slides inside a song, dispatch presses one key per slide, 60 ms apart. With WorshipTools the guard is checked before every key, so if the operator clicks another window during the step, a later key is refused. The error returns before `sent.global` is updated, so Voxxa still believes the screen is where it started, although some keys went out. From then on the screen is ahead of what Voxxa believes. At the song's last slide Voxxa can press one Right too many, which shows Presenter's next service item: exactly what ADR-019 § 3 forbids. A failed enigo call partway had the same drift before Q9W; the guard makes a halfway stop realistic.
**Where.** `src-tauri/src/dispatch.rs:157-179` (the stepping loop, `?` on each key, and the position recorded only at `:179`); the guard in `src-tauri/src/presenters/keystroke.rs:206-209`. Ponytail review should-fix 1; the comparator's disagreement 2; R0 item 18 ("left as is").
**Why.** A wrong service item goes up in front of the congregation, and the amber ask does not appear, because Voxxa does not see a song change.
**Suggested fix.** In the loop, record the keys actually sent before returning the error, for example `if let Err(e) = r { sent.global = Some(cur + delta.signum() * i as i64); return Err(e); }`. Or check the guard once before the loop through a driver method. Add a fake-driver test where the second `next()` fails and assert that `sent.global` moved by exactly one. "Everything else in src-tauri/src" has 2 lines left (Q9W-04), so this needs lines found first or a budget decision.

## Q9W-02 [medium, adr] Founder: confirm the F10 unblank key (T3)
**What.** F10 clears the lyrics from Presenter's main screen (test card T3), but how to bring them back was not tested. So the WorshipTools profile has no blank key and reports `can_blank: false`: Voxxa skips its own blanks at prayers, and the operator's Blank says "not supported". The lyrics stay up through a prayer unless the operator clears them by hand.
**Where.** `src-tauri/src/presenters/keystroke.rs:164` (the WorshipTools key map, `blank: None`); `:268` (`can_blank` from the key map); ADR-019 § 4 and its review trigger; founder checklist M15 (`handoff.md`).
**Why.** ADR-011: lyrics should not stay on screen where they do not belong. Until the unblank key is known, a blank Voxxa can't undo would be worse than none.
**Suggested fix.** The founder presses F10 in Presenter on LHMEZPC01 and finds the key that brings the same slide back (F10 again, or another key). Then, in a follow-up: set the profile's blank key. If the unblank key differs from F10, `unblank()` needs a change too: today it presses the blank key again (`keystroke.rs:328-331`), update the key-map test, the runbook and INTEGRATIONS, and amend ADR-019 § 4. `can_blank` turns on through the key map with no dispatch change.

## Q9W-03 [low, adr] When the operator misses the ask, the next Right shows Presenter's next item and the light turns green
**What.** On a song change Voxxa presses nothing and asks 'Put "<song>" live in Presenter.' If the operator does not, the next step inside the new song presses Right, and Presenter, still on the old song's last slide, moves to its next service item. That counts as a delivered slide, so the light turns green ("Following <song>…"). The amber ask, the only protection ADR-019 § 3 names, disappears exactly when the wrong item is showing.
**Where.** `src-tauri/src/dispatch.rs:151-156`; `src/simple/simple.js`; ADR-019 § 3 "Limit" and the base-merge amendment 3. Ponytail review nit 7. The runbook and M16 already describe the symptom (38f043d).
**Why.** Voxxa is blind to Presenter's screen, so a missed ask becomes a wrong item on the audience screen.
**Suggested fix.** As a follow-up, hold every key in a new song until the operator confirms it (for example a "Done" on the amber light, or the slide strip). Decide in an ADR-019 amendment whether the extra click is acceptable. Until then, M16 checks the symptom live.

## Q9W-05 [low, security] Any program named Presenter.exe counts as WorshipTools Presenter
**What.** `is_presenter_exe` matches the last path segment `Presenter.exe` or `Presenter` in any folder, in any case. Any other program with that name is found by discovery and passes the foreground guard.
**Where.** `src-tauri/src/presenters/keystroke.rs:54-57`; ADR-019 § 1; test card T1; R0 item 18; ponytail review nit 8.
**Why.** "Presenter" is a common name. The worst such a program can get is Right or Left while it is in front, but a wrong match also means Voxxa believes Presenter is running when it is not.
**Suggested fix.** Since the full path is read anyway (`QueryFullProcessImageNameW`), require the folder too (`…\Presenter\Presenter.exe`), or read the file's product name or signer. M15 checks the booth PC live. Keep the name-only match for the guard if a portable install is likely.

## Q9W-06 [low, security] Discovery and the guard open a read-only handle on Presenter's process
**What.** To read each process's path, discovery calls `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` on every process, and the guard does it on the front process (often Presenter) before every key. Nothing is sent to Presenter and its state does not change. The ponytail lane used a Toolhelp32 snapshot, which opens no process handle at all.
**Where.** `src-tauri/src/presenters/keystroke.rs:67-115` (`process_path`, `process_paths`); the comparator's disagreement 1 (`2026-11-20-ponytail-q9w.md` § 4).
**Why.** The safety rule says Presenter's process stays untouched. The comparator read that as "no keys, no focus, no window contents, no stopping", which a query handle meets. If the founder means "no handle at all", this changes.
**Suggested fix.** Founder decision. If no handle is wanted, take ponytail's Toolhelp32 snapshot (`q9w/ponytail` 82bdf71, about 35-50 lines in `keystroke.rs`, which is at 396 / 400, so lines must move first) and accept that only the exe name, not the path, is known (see Q9W-05).

## Q9W-07 [low] Presenter run as administrator drops Voxxa's keys, and Voxxa cannot tell
**What.** Windows (UIPI) silently drops keys that an ordinary program sends to a program running as administrator. Nothing moves in Presenter, and the light stays green or amber. The runbook and INTEGRATIONS say so, and M15 checks it; the app does not detect it.
**Where.** `docs/runbooks/presentation-app-not-reachable.md:76-79`; `docs/INTEGRATIONS.md` ("Run Presenter normally"); security record, Q9W.
**Why.** A volunteer who once ticked "Run as administrator" gets a Voxxa that seems to work but never moves a slide.
**Suggested fix.** When the guard finds Presenter in front, check whether its process is elevated and Voxxa is not (for example `OpenProcessToken` failing with access denied, or `TokenElevation`), and show an amber sentence ("Presenter is running as administrator, so it ignores Voxxa's keys."). Count it in the presenters row (`keystroke.rs` 396 / 400).

## Q9W-08 [low] With WorshipTools, Voxxa's own window in front shows the red row, not the amber sentence

## Q9W-09 [low] After a song change that lands mid-song, the stage shows the conductor's slide while Presenter shows the first slide
**What.** If the conductor's first detection in a new song is a later slide, dispatch records the song's first slide as where the screen is (`sent`), but `slide-advanced` carries the conductor's target slide, index and text. The stage window and the song strip are ahead of Presenter until the next step, which presses the Rights that close the gap.
**Where.** `src-tauri/src/commands/mod.rs:308-320` (the event); `src-tauri/src/dispatch.rs:155`; SDE record, Q9W base merge, "Residual".
**Why.** Singers reading the stage display see a later slide than the audience screen for a few seconds.
**Suggested fix.** On the ask path, send `slide-advanced` for the slide `sent` records (the song's first slide), not the conductor's target. Needs about 2 lines in "everything else" (Q9W-04) and a test in `tests/worshiptools.rs`.

## Q9W-10 [low] After the operator's raw Next past a song's end, Voxxa still asks for the next song
**What.** The operator's raw Next/Prev (`dispatch::step`) moves `sent.global` but not `sent.song`, as ADR-019 § 3 requires. If the operator steps past a song's end, Presenter moves to its next item, and when the conductor then detects that song, dispatch sees a song change and asks 'Put "<song>" live in Presenter.', although the operator already moved on.
**Where.** `src-tauri/src/dispatch.rs:189-208` (`step`); `:151`. Ponytail lane's risks.
**Why.** An extra ask is safe (no key is pressed) but confuses the volunteer.
**Suggested fix.** Leave it, or document it in the runbook's WorshipTools section ("if Voxxa asks for a song that is already live, click the slide being sung"). A code fix would have to guess which item Presenter moved to, which Voxxa cannot see.

## Q9W-12 [low, documentation] INTEGRATIONS says the set-up guide connects Presenter; it does so on its own only when Presenter is the only app found
