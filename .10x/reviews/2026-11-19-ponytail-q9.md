## 1. The task, in short
Wire Call for help to `generate_diagnostic_report`, plus an export of the operator's `localStorage` and the last 2 minutes of hypotheses from the session log. Zip them to the Desktop, show them to the user before writing, then open the support e-mail draft. Write three runbooks (`no-audio-device`, `presentation-app-not-reachable`, `model-missing`) and link each from the matching red status. Write a one-page Windows quick-start. No telemetry. Exit: the bundle is produced, and the links resolve.

User decisions (binding, 2026-11-19; handoff, "User decisions for Q9"):
1. **Privacy first.** Fix #102 (Q7-08) before anything else, in its own commit with a test: no recognised text may reach the diagnostics ring buffer or the report. The recent words go into the zip only as a separate file. A review screen lists every file and shows the words file, with a checkbox, on by default, "Include the last 2 minutes of words the app heard"; unchecked means the file is absent. Secrets are redacted from the settings export, with a test. Nothing is written before the user confirms.
2. **Support e-mail.** No recipient yet: one named constant, left empty, and a ticket. After writing, open the draft (subject and a short body naming the file and where it is) and the zip's folder. No network call of any kind.
3. **Budget.** Fit the existing rows. No cap raised, no row added; if it cannot fit, stop and report.
4. **GUI testing** as in Q8: a mocked browser, and a guarded scratch build of the real app. In the real app, a bundle may be written only to a scratch folder, never the real Desktop, and the e-mail and open-folder step is never triggered. The usability script is re-run only for the Call-for-help step.
5. **Backend.** New commands are allowed. Existing command signatures and behaviour stay unchanged, apart from the #102 fix. Reuse `zip` and `dirs`; no new crate unless unavoidable.

## 3. Cross-reviews

### Review of the 10x lane (7797556..dadcdbb)
**Verdict: ship; one should-fix worth making before merge, and one nit.**
- **Should-fix.** `open_help_email` opened the draft first and the folder second, stopping at the first error. On a church PC with webmail and no `mailto:` handler, a failed draft means the folder never opens, and the folder is the part that matters, because a `mailto:` link cannot attach the file.
- **Nit.** `open_help_email` returned the two targets, and nothing read them.
- **Strengths named:** #102 has a real test, and every log call outside `cli/` was audited; nothing is written before Save, `create_new` never overwrites, a failed zip is removed, and a second Save is refused; the webview cannot choose what is opened (no argument, three-name whitelist); redaction covers every key the GUI stores; the session-log order matches `voxxad`'s naming, including `-10` after `-2`; the docs' claims match the code.
- Re-run by the reviewer: `help_bundle` 8/8, `test:gui` 7/7, e2e 158/158, budgets OK, the `dictat` grep empty.

### Review of the ponytail lane (7797556..8f87206)
**Verdict: approve with four should-fixes.**
1. The same e-mail-order problem: if the `mailto:` open fails, the folder never opens, and the body says it has.
2. `openHelp` is not re-entrant, and the focus stays on the Call for help button behind the overlay. Enter can open the review again, which creates two checkboxes with the same id; Save reads the first, so a volunteer who unticks the visible one can still get the words file written. That breaks "unchecked means absent".
3. The presentation-app runbook leaves out OpenSong's API key, which is sent as `args.password` (`src/main.js:1283-1284`) and never saved (`src/main.js:1297-1303`).
4. The words file can come from a `voxxad` session up to 14 days old, while the label says "the last 2 minutes".
- **Nits:** synchronous commands on the main thread; toasts drawn above the review overlay; the runbook base URL untested and any `[a-z-]+` name accepted; a partial zip left behind on a failed write; a `u64` overflow in the words window on a malformed log.
- The reviewer also reported 19 headless Edge processes with `%TEMP%\voxxa-verifya3-*` profiles, started at 1:16-1:18 PM, that no Q9 agent started (see § 8).

## 4. The comparator's ruling
**Base: the 10x lane at dadcdbb.** Both lanes meet the exit criteria. 10x wins on the user's first priority, privacy, and on safety:
1. **"Unchecked means absent" holds in edge cases.** The ponytail dialog can be opened twice (review should-fix 2). The 10x dialog drops stale previews with a ticket guard, makes `#simple` inert and closes on Escape.
2. **The bundle stays in the backend.** Save can write only the previewed files, optionally without the words file. In the ponytail lane the webview passes any (name, content) pairs to be written, and every `localStorage` key is exported, where 10x exports only `voxxa.*` keys.
3. **The QA override is safer.** Under `VOXXA_HELP_DIR`, the 10x `open_help_email` opens nothing, so the rule against opening the mail program and Explorer is enforced in code. The 10x runbook check is a three-name whitelist.
4. **Records and tests.** ADR-018 was committed first and ADR-017 is amended. 10x has more regression tests (8 Rust tests, links resolve in Rust and in Node, e2e 158 against 144).
5. **Review findings.** One should-fix and one nit against four should-fixes; three of the ponytail findings also apply to 10x and became grafts.
6. **The words file names its source log**, which partly answers the stale-session concern.

The cost is simplicity: the 10x backend is about 223 lines against about 140, and leaves 16 lines in the backend row against 74.

**Grafts** (all applied on `q9/base`, one commit each):
1. **064c4c8** OpenSong with an API key needs the key again after every start (ponytail review, finding 3).
2. **42ca27f** a presentation app on another computer: same network, and Host is that computer's address (ponytail runbook).
3. **82d24e9** `pub fn runbook_url(name) -> Option<String>`, with a test of the exact GitHub URL and `None` for `../../evil` (ponytail review, nit 7).
4. **caa67b1** the words window uses `saturating_sub`; the new test case panicked with "attempt to add with overflow" on the old line (ponytail review, nit 9).

**Review fixes:** **9917115** opens the zip's folder first and the draft second, so the folder is open whatever happens to the draft, and returns `Result<(), String>` (the 10x review's should-fix and nit). A folder error starts with `folder: `; the GUI's message then says whether the folder is open. ADR-018 §§ 5, 6 and 9 were updated.

**Disagreements, and how they were settled:**
1. **Simplicity against safety.** Ponytail is the smaller design with more budget left, and its JS redaction is short and tested. Kept 10x for the backend-held bundle, the override that opens nothing and the re-entrancy-safe dialog. The backend row now has little room left (6 lines at the final head), so the next step that touches `src-tauri/src` outside its own rows must make room first.
2. **Which session log.** 10x picks by name (`voxxad`'s naming, `cli/voxxad/main.rs:310-340`, tested); ponytail by modified time. Both work; kept 10x.
3. **An old session's words** (ponytail review, should-fix 4). Partly answered by the 10x header; kept as ticket Q9-08, not a merge fix.
4. **Toasts above the overlay.** Not verified in the 10x screenshots at the time, so left as a ticket. The CSS confirms it applies to 10x too (Q9-09).
5. **A stale preview in 10x.** If a cancelled preview finishes after a newer one, the pending bundle can differ from what the report shows. Privacy still holds, because `includeWords` is false whenever no checkbox is shown or it is unchecked. No fix.

## 9. Lessons for the next step
- **Test the command, not only its helpers.** Round 1's survivors lived in the glue between the pure functions and the Tauri command. Run the real command in its own test process with the QA override.
- **Order side effects so the important one happens first.** The folder is what the volunteer needs; the draft is a convenience.
- **Keep what was reviewed on the trusted side.** Holding the previewed bundle in the backend made "write exactly what was shown" a property of the code, not of the dialog.
- **A docs page is checked against the release process too.** "Download from the releases page" was true of the plan, not of the repository.
