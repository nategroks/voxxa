## 7. Linux and macOS risks carried to CI

- `tauri-plugin-single-instance` pulls zbus (D-Bus) on Linux: +32 lock packages, first compiled on CI.
- The stage no-activate path is Windows-only; `focusable: false` on macOS/Linux and `is_focused()` semantics are unverified (ticket Q2-52).
- `tests/model_download.rs` uses local TCP servers and timing; a CI runner with a proxy that does not bypass localhost, or a very slow runner, could make it flaky.
- `tests/importer_slides.rs` relies on pdf-extract 0.12.1 panicking on the two fixtures and on `.gitattributes` keeping the PDFs binary.
- Audio defaults on CoreAudio and ALSA/Pulse are untested; a device offering only U8 or I32 now fails with a clear error.

### 8.1 The audit report

The report is reproduced as the auditor wrote it, with the headings shifted down. The only hymn text in it is from the public-domain examples. The quoted one-word inputs ("Oh", "soul", "the", "me" and so on) are probe inputs, not lyrics.

> **Ponytail audit, Q2 lane: `C:/dev/q2-find` @ 3446e09 (code head b09373d)**
>
> **What this repo does:** Voxxa is a Tauri 2 desktop app for churches. It listens to the room, turns speech into text with Whisper (a speech-to-text model that runs on the laptop), works out which song and verse is being sung, and moves the slides in the church's presentation app. It blanks that app's screen when nobody is singing. It never projects lyrics itself (ADR-011).
>
> **Load I assumed:** one Windows church laptop, one operator and one service at a time, with 4 to 10 songs and at most 50. Inputs that cannot be trusted: imported files, the local HTTP API, and network presenters. The worst failure is wrong words on the audience screen. A black screen is acceptable.
>
> **Gates (run on a clean `git archive` copy, so the target tree was not touched):** 1 build OK · 2 fmt OK · 3 clippy OK · 4 tests OK (45 lib tests plus every integration test) · 5 cargo-deny OK (one warning: `voice_activity_detector` has no licence field) · 6 budgets OK, but "everything else" is at **2489 / 2500** and the GUI at **2951 / 3000**, so new code in `commands/` must be paid for with deletions · 7 dictat grep: empty.
>
> **Must fix**
>
> 1. **One short word from Whisper starts a song or brings lyrics back during a prayer** (`src-tauri/src/aligner/mod.rs:311-409`)
>    - **What this is:** `Conductor::on_transcript` decides from each Whisper transcript whether to show, move or unblank.
>    - **Problem:** Nothing sets a minimum length. A 1-3 letter string scores 100 against any slide that contains it. I ran a probe on the public-domain example setlist. With nothing detected yet, `"Oh"` gave `Goto(2,3)` and `"soul"` gave `Goto(2,0)`. With a one-song setlist, `"you"`, `"Thank you."` and `"Amen."` each started the song. After a song had ended and been blanked, `"the"` and `"me"` brought back Amazing Grace, and `"Oh"` switched to verse 4 of It Is Well. Whisper often prints words like these for music, coughs and applause.
>    - **Fix:** One guard after `self.on_speech(now)`: `if text.split_whitespace().count() < 4 { return Action::Noop; }`. I tried it in the scratch copy: all 45 lib tests still pass and the probe produces no Goto. Add the probe as a test.
>    - **If we skip it:** Lyrics appear during announcements and prayers, and a single "Oh" can put the wrong verse of the wrong song on screen.
>
> 2. **The check "is Voxxa focused?" misses Voxxa's own tray menu and file dialog, and may never be true on Windows** (`src-tauri/src/commands/mod.rs:395-400`, `tray/mod.rs:42-73`)
>    - **What this is:** Before it sends a key, the keystroke driver refuses to type if a Voxxa window has the keyboard. It asks each webview window for `is_focused()`.
>    - **Problem:** The tray menu runs `SetForegroundWindow` on tray-icon's hidden window (`tray-icon-0.25.1 windows/mod.rs:554`), and the file-open dialog is a separate native window. Neither is a webview window, so the check says "not focused". Tray **Blank** then sends "." to that hidden window and still records `sent.blank = true`. The next unblank toggle then blacks out the lyrics, and from then on every blank is inverted (the Q0 #2 failure comes back). During an import, the conductor's arrow keys go into the file dialog, but `sent.global` still moves, so every later slide is off. Second issue: tauri uses tao's `is_focused` (`is_active && is_focused`), and wry moves keyboard focus into the WebView2 child window. So the main window may read "not focused" even while the operator is clicking in it, which would let Next type into Voxxa forever (the Q0 #3 loop). I could not run the GUI to confirm this.
>    - **Fix:** On Windows, define "Voxxa has the keyboard" as "the foreground window belongs to this process": `GetWindowThreadProcessId(GetForegroundWindow(), &mut pid); pid == std::process::id()`. That is about 8 lines with an `extern "system"` block, like `show_stage`. Keep `is_focused` on other platforms. Check by hand once: keystroke driver, click Next in Voxxa, and the log must show the focus refusal.
>    - **If we skip it:** One click on the tray's panic Blank can invert the blank state for the rest of the service.
>
> 3. **A Blank that fails or is refused is never retried, so lyrics stay up through the prayer** (`aligner/mod.rs:286-306, 430-436`; `commands/mod.rs:222-227`)
>    - **What this is:** `tick()` and `blank_hold()` set `is_blank = true` and return `Blank`. The listening loop sends it and, on an error, only logs it and shows a toast.
>    - **Problem:** The conductor already thinks the screen is blank, so it never sends Blank again. Two cases: (a) the operator has Voxxa focused when the song ends (keystroke refusal), or (b) ProPresenter or OpenLP misses one HTTP call. In both cases the last slide stays on screen through the prayer and sermon. The next tick does nothing, because `BlankHold && is_blank`.
>    - **Fix:** When dispatching a `Blank` returns an error (except `Unsupported`), set the conductor's `is_blank` back to false so the next 200 ms tick retries. Only send a new toast when the error text changes. Add one test with a presenter that fails once and then succeeds.
>    - **If we skip it:** A short network hiccup or a stray click leaves lyrics on screen during the rest of the service.
>
> 4. **Drivers that jump to a slide number assume Voxxa's slide list matches the app's, and nothing checks it** (`src-tauri/src/dispatch.rs:301-316`; `planning_center/mod.rs:180-218`; `importers/pro7.rs:34-50`)
>    - **What this is:** For ProPresenter REST and FreeShow, the dispatcher sends `goto_slide(slide_in_song)`. The title check only confirms that the right presentation is selected.
>    - **Problem:** A Planning Center import lists each section once (Verse 1, Chorus, Verse 2, Bridge). The app's arrangement repeats sections (Verse 1, Chorus, Verse 2, Chorus, Bridge...). So Voxxa's slide 3 (Bridge) triggers the app's slide 3, which is the Chorus: wrong words on screen. The `.pro7` importer has the same problem: it drops slides with no text, slides shorter than 3 characters, and a block identical to the one before it, so every later index is shifted.
>    - **Fix:** For drivers that can report state, read the app's slide count for the selected presentation (Pro7 REST `/v1/presentation/active`) when a song starts. If the count differs from Voxxa's, blank and show "this song's slides differ from the app; import the app's own file". In `pro7.rs`, keep short blocks as empty slides instead of skipping them. Planning Center plus ProPresenter is the most common setup, so this needs an endpoint check against a real ProPresenter.
>    - **If we skip it:** With a repeated chorus, the bridge text shows while the room sings the chorus.
>
> 5. **ProPresenter WebSocket and OpenSong jump to slide numbers in the wrong place** (`presenters/propresenter7_ws.rs:232-249`, `presenters/opensong.rs:161-167`)
>    - **What this is:** The `goto_slide` code for these two drivers.
>    - **Problem:** The WebSocket driver always sends `presentationPath "0:0"`. In ProPresenter's remote protocol that is a playlist position (playlist 0, item 0), not "the selected presentation" as the code comment says. So every jump triggers a slide of the first playlist item. OpenSong's `/presentation/slide/N` most likely counts across the whole set, while Voxxa sends the index inside the song. Neither driver can report state, so the title check passes on any operator action. Both claims are unverified against the real apps.
>    - **Fix:** Set `can_goto_slide: false` on both drivers, as OpenLP already does. They then step with next/previous inside the selected presentation, which the dispatcher already supports (OpenSong is already handled as a toggle driver). Two one-line changes.
>    - **If we skip it:** Song 1's slides appear while song 3 is being sung.
>
> **Should fix**
>
> 6. **Long singing with no pause produces no text; quiet noise adds up to "speech"** (`src-tauri/src/vad/mod.rs:97-130, 155-162`). Still open from Q0 #14. The VAD passes an utterance on to Whisper only after 300 ms of silence. Over a band there may be no 300 ms gap, so no slide moves until the first pause; the whole buffer, possibly a minute long, then becomes one late transcript, and the buffer grows without limit. `speech_samples` is never reset by a silent frame before speech starts, so scattered noise blips add up to 250 ms and count as speech. Fix: when `speech_buffer.len() >= 5 * 16000`, return it even without a pause; when a frame is silent and `!is_speech`, set `speech_samples = 0`. About 4 lines and one test. If we skip it: slides stay on one verse for a whole section and then jump late.
> 7. **If the model is slower than real time, the delay grows without limit** (`commands/mod.rs:264-316`, `audio/mod.rs:272`). One thread transcribes and the audio channel has no size limit. With Medium or Large V3 Turbo on a laptop with no GPU, 5 s of audio can take longer than 5 s to transcribe; unread chunks pile up, decisions are made on ever older audio, and memory grows. Unverified: no benchmark. Fix: after each `transcribe`, if it took longer than the audio it covered, emit one warning ("this model is too slow for this computer, pick Base"), drain the queued chunks (`while rx.try_recv().is_ok() {}`) and reset the VAD. About 6 lines. If we skip it: on ordinary hardware with a big model, listening becomes useless during a service.
> 8. **EasyWorship import refuses every real library and offers no way to pick songs** (`src/main.js:270-283`, `aligner/mod.rs:124-133`). A `.db` import loads the whole library as the setlist; Q2 added a 50-song limit, so any library over 50 songs fails with "pick today's songs", but nothing in the app lets the operator pick. ### 8.3 Where the audit and Q2 disagreed, and the adjudication

**Three new items above the fix-now bar that Q2 had not recorded:**
- **PT2-01: fix-now, High (the audit said Critical).** Reproduced with a scratch probe. Q2-02 had been checked only with long prayer transcripts. A one-word transcript ("the", "me", "Lord") re-showed the lyrics after a blank, and "Oh", "soul" or "God is good." started a song from Listening. The probe also found a case the audit missed: with a one-song setlist, every ordinary announcement started the song (8 of 8 sentences, for example "Good morning everyone, please take your seats."), so the audit's 4-word gate alone was not enough. Adjudicated fix: the 4-word gate, plus "the new transcript must itself read as the song" before any song start. Rated High, not Critical, to match Q2-02 (same class: wrong content on the audience screen, no crash). Q2-47 had mentioned a short-transcript filter only as tuning for the mid-song blank.
- **PT2-02: fix-now, High (the audit said plausible).** The tray half was confirmed in tray-icon 0.25.1: the tray menu makes Voxxa's hidden tray window the foreground, so `voxxa_focused()` was false and a Keystroke tray Blank typed '.' into Voxxa itself. `Sent.blank` then inverted (the Q2-03 inversion again). Q2's founder check M11 had assumed tray Blank works. The WebView2 `is_focused` half is **not accepted as shown**: wry calls MoveFocus inside WM_SETFOCUS, so tao probably ends with focused = true. It stays for founder check M5; the foreground-process fix covers it either way.
- **PT2-05: fix-now, High.** Checked against the protocol docs. In the ProPresenter 6/7 remote protocol, presentationPath "0:0" is "the first presentation of the first playlist", not the selected one. OpenSong slide numbers identify a slide across the whole set. Since Q2-05 both drivers received `slide_in_song`, so a confirmed song change showed a slide from the wrong presentation. Q2-05 had classed these drivers as "chip confirms" but never checked what their index means.

**Existing tickets the audit wanted promoted; kept as tickets:**
- **PT2-03 / Q2-46 (refused Blank not retried).** The result is a missed blank (the last lyric stays up), which is the Q2-23 Medium precedent, not a wrong slide; the next match re-syncs. The audit's 200 ms retry is not safe as stated: on the single listening thread with a 3 s network timeout it would stall transcription and spam toasts. Because the PT2-02 fix makes refusals more frequent, Q2-46 should be the first item of Q3, with backoff.
- **PT2-04 / Q2-45 (slide-list mismatch).** No smallest fix can be verified offline: `PresenterState` has no slide count, and keeping short pro7 blocks as placeholders risks phantom slides for theme labels and footers. The ticket is widened to Planning Center arrangements (a new, unverified aspect). Promote if founder check M9 shows a mismatch.
- **PT2-06 / Q2-20 (VAD).** No new evidence; the M3 promotion rule stands.

**Severity differences, no change of decision:** PT2-15 / Q2-15 and PT2-16 / Q2-26: the audit said Low, Q2 says Medium (skeptic-adjudicated); kept Medium. PT2-08: the audit called it a blocker; it does not meet the bar (no crash, no data loss, no wrong content), so it is its own ticket (Q2-57) and cut-list evidence.
