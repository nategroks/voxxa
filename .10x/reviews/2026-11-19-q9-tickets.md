## Q9-01 [low, documentation] Set the support e-mail address
**What.** The Call for help e-mail draft has no recipient. The address is one named constant, `SUPPORT_EMAIL`, left empty on purpose (user decision 2, 2026-11-19), so the volunteer types their tech lead's address every time.
**Where.** `src-tauri/src/help/mod.rs:16`. The test that pins it empty: `the_email_draft_names_the_file_and_has_no_recipient` (`src-tauri/tests/help_bundle.rs:402`). The words that tell the volunteer to type an address: `docs/quick-start.md:38-41` and `src/simple/help.js:77`.
**Why.** A volunteer under pressure on a Sunday morning may not know whom to write to. ADR-018's review trigger names this.
**Suggested fix.** The founder chooses the address (a support inbox, or one per support-tier church). Then set the constant, change the test to expect it in the `mailto:` URL, and change the quick-start and the dialog's sentence. If the address differs per church, decide first whether it becomes a setting (a GUI change in Advanced) instead of a constant.

## Q9-02 [medium, privacy, adr] No words file on GUI-only machines until the GUI writes session logs
**What.** The words file comes only from `voxxad`'s session logs, because the GUI writes none (Q3-09, #53). On a church PC that runs only the GUI, the review says "Voxxa found no record of words it heard" and shows no checkbox, so the bundle has two files.
**Where.** `src-tauri/src/help/mod.rs:94` (`recent_words`); `src/simple/help.js:61`; ADR-018 § 2.
**Why.** The words are the most useful part of a wrong-slide report, and the pilots will run the GUI.
**Suggested fix.** Decide with #53, #49 (14 days of transcripts in the roaming profile) and #99 (default file permissions) whether the GUI keeps a short session log, where (local, not roaming), and for how long. Record it in an ADR amendment. Until then, the bundle stays as it is.

## Q9-03 [low, security] Move from the shell plugin's deprecated `open` to `tauri-plugin-opener`
**What.** The e-mail draft, the zip's folder and the runbook URL are opened with `tauri-plugin-shell`'s `open`, called from Rust under `#[allow(deprecated)]`.
**Where.** `src-tauri/src/help/mod.rs:168-172`; ADR-018, Alternatives.
**Why.** The shell plugin points to `tauri-plugin-opener` and may drop `open` in a later 2.x or 3.0 release. Today it needs no capability and no new crate.
**Suggested fix.** In its own PR, add `tauri-plugin-opener`, call it from Rust only (keep the webview without an opener capability), and check `cargo-deny` and the `tests/capabilities.rs` test.

## Q9-04 [low, documentation] Runbook links need a browser and the internet
**What.** "What to do" opens the runbook on GitHub (`https://github.com/nategroks/voxxa/blob/main/docs/runbooks/<name>.md`). A booth PC that is offline, or whose browser is locked down, cannot open it. Until `q9/base` is merged, the three URLs also return 404, because `main` does not have the files yet.
**Where.** `src-tauri/src/help/mod.rs:230` (`runbook_url`); ADR-018 § 7.
**Why.** A red light is the moment the volunteer needs the steps, and network trouble can be part of the problem.
**Suggested fix.** Ship the three runbooks with the app (bundled resources) and open the local copy, or show each runbook's steps in a small dialog. Weigh the lines against the backend row (2,494 / 2,500) and the Simple mode row (436 / 600).

## Q9-05 [low] The zip name is in UTC, and the folder opens without the file selected
**What.** The zip is named from the UTC time, so a save at 3:27 PM local time can be named `voxxa-help-…-2127xx.zip`. Explorer opens the folder but does not select the file.
**Where.** `src-tauri/src/help/mod.rs:206-207`; `email_targets` (`src-tauri/src/help/mod.rs:156`).
**Why.** On a crowded Desktop the volunteer has to find the right zip by name, and the name does not match the clock.
**Suggested fix.** Use local time (the `time` crate's local offset, with UTC as the fallback), and open the folder with the file selected (`explorer /select,<path>` on Windows), still from Rust and still never under the QA override.

## Q9-08 [low, privacy] The words file can come from an old `voxxad` session
**What.** The words file holds the last 2 minutes of the newest `voxxad` log, however old it is. `voxxad` keeps logs for 14 days, so the words can come from a session a week ago, possibly one the volunteer did not run. Only the file's header names the log, and with it the date; the checkbox says "the last 2 minutes of words the app heard".
**Where.** `src-tauri/src/help/mod.rs:94-111` (the header at `:109`); `src/simple/help.js:38`; `src/cli/voxxad/main.rs:310`.
**Why.** Privacy first: the volunteer should see at a glance where the words come from before sending them.
**Suggested fix.** Show the session's date and time next to the words file in the review (for example "from the session of 12 Nov, 10:42"), or leave out logs older than today. The label text is a user decision; keep the agreed wording and add the date beside it.

## Q9-09 [low] Error toasts draw above the Call for help review
**What.** The toast container has `z-index: 1100`; the review overlay (`.fr`) has `z-index: 1000`. Error toasts therefore cover part of the review, including the buttons, for up to 6 s.
**Where.** `src/styles/main.css:858`; `src/simple/simple.css:25`. The ponytail lane's screenshot `17a-help-review.png` shows it on that lane's dialog, which uses the same overlay class.
**Why.** People press Call for help exactly when error toasts are likely (the presenter-error and mic-lost toasts repeat).
**Suggested fix.** Raise `#help` above the toasts while it is shown (in `src/simple/simple.css`, not in `main.css`), and add an e2e check that the Save button is the element at its own centre point while a toast is shown.

## Q9-11 [low, tests] Two test gaps the verifiers left: a Debug-level heard-text line, and the preview command's glue
**What.**

ADR-018 § 1 says the text is not logged at any level.

## Q9-12 [low, tests, documentation] The e-mail and folder step has never run on a real PC, and webmail is not covered
**What.** By rule, no Q9 agent opened a mail program or Explorer. Only the `mailto:` URL and the folder path are tested, in Rust. On a PC with no `mailto:` handler (common where a church uses webmail), Windows may show an app picker or return an error. The folder opens first either way (9917115), but neither the quick-start nor the dialog says what a webmail user should do. Nobody has checked how classic Outlook decodes a percent-encoded path with a non-ASCII user name.
**Where.** `src-tauri/src/help/mod.rs:218-228` (`open_help_email`); `src/simple/help.js:77-82`; `docs/quick-start.md:38-41`.
**Why.** The draft is how the bundle reaches the tech lead.
**Suggested fix.** In the founder's run (Q9-07), try Save once with the installed mail program and once on a PC without one. Add one line to the quick-start's Call for help section: "If you use webmail, open it yourself and attach the file from the folder that opened."

## Q9-13 [low, performance] The words file reads the whole newest session log into memory
**What.** `recent_words` reads the newest session log with `read_to_string` and parses every line before it keeps the last 2 minutes.
**Where.** `src-tauri/src/help/mod.rs:99-100`.
**Why.** A long `voxxad` session (hours of `tick` lines) is read and parsed in full each time the review opens. The command is async, so the window does not freeze, but the review waits. Fine at today's file sizes.
**Suggested fix.** Read only the tail of the file (for example the last 1 MB), or stop parsing lines older than the window once the end time is known. Add a test with a large placeholder log.

## Q9-14 [low, privacy] The review does not say what the report holds besides diagnostics
**What.** `diagnostic-report.json` holds the audio device names (which can contain a person's name), the current song title, conductor log lines with titles, and presenter error text. ADR-011 and ADR-018 § 2 allow this, and the review shows the report one click away, but the review's sentence does not say it.
**Where.** `src/simple/help.js:60`; ADR-018 § 2 and Consequences.
**Why.** Privacy first: the volunteer should know before sending that song titles and device names are in the report.
**Suggested fix.** For Q11's security review of the bundle ("review the support bundle for over-collection"): decide whether device names and titles stay, and if they do, add a short line to the review ("The report names your microphone and the current song."). Fits the Simple mode row.

## Q9-15 [low, tooling] The real-app driver compares two spellings of the scratch folder
**What.** `scripts/qa/call-for-help-real-app.mjs` checks that the zip is in the scratch folder with `path.resolve` on both sides. When `VOXXA_HELP_DIR` is given to the driver in its long form and to the app in its 8.3 form (`LIGHTH~1`), the check fails although the zip is in the right folder. It cost one re-run at the finish (11/12, then 12/12).
**Where.** `scripts/qa/call-for-help-real-app.mjs:78`.
**Why.** A false failure in a safety check invites people to stop trusting it.
**Suggested fix.** Compare `fs.realpathSync.native` of both paths.

## Q9-16 [low, security] Settings redaction works by property name only
**What.** A secret is redacted only when its property name reads as one (`token`, `secret`, `pass`, `key` and the rest, ADR-018 § 4). A secret stored under a harmless name would be exported. No such key exists today: passwords and the HTTP API token are not in `localStorage` (`src/main.js:1131-1133`), and Planning Center credentials stay in memory (`src/main.js:157`).
**Where.** `src-tauri/src/help/mod.rs:47` (`is_secret`); `:54` (`redact`).
**Why.** Every new setting that holds a secret has to be named so the rule catches it.
**Suggested fix.** Add a test that reads every key `src/` writes to `localStorage` (a grep of `localStorage.setItem`) and fails on a key the export has not seen before, so a new setting gets a deliberate look. Optionally redact values that look like tokens (long base64 or hex strings).
