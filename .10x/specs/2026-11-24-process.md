# voxxa development process: three senior engineers, a UI consultant, an engineer team, and the founder

Date 2026-11-24. This extends the process already in use (10x-team with `.10x/` records, ADRs before code,
an independent ponytail lane per step, line budgets, the eval gate; `.10x/specs/2026-11-11-prompts-10x-team.md:5-21`).
It does not replace it. Whether the roles below are people, contractors or agent lanes is founder item FA-07;
the default is **agent lanes now**, with the founder as the only human gate.

## 2. How a step runs

```
founder batch (pre-approvals, cost)  ─►  ADR Accepted?  ──no──► write/amend ADR, stop at the founder gate
                                             │ yes
                                             ▼
                        ┌──────────── two lanes off main ────────────┐
                        │ vN/10x: /10x-Team:10x-team, the named roles │   (measurement and close steps:
                        │ vN/ponytail: ponytail full + review/audit   │    10x + ponytail-audit only)
                        │ (never sees the 10x lane's output)          │
                        └───────────────┬─────────────────────────────┘
                                        ▼
                comparator (EM): pick or merge per hunk; cross-reviews (each lane reviews the other)
                                        ▼
                adversarial verifiers: A = safety/privacy lens, B = feasibility/correctness lens
                                        ▼
                gates: fmt · clippy · tests · cargo deny · budgets · replay determinism · eval gate
                       · media/private-data guard · kit_check · named safety tests · release_config
                                        ▼
                QA + security review files ─► state files ─► founder-approved outward actions ─► merge
```

1. **Before:** the EM sends one founder batch per step (or per week): what will run, the cost band, the
   pre-approvals needed (push, PR, CI fixes, merge when green, tickets, comments), and any decision.
2. **ADR first.** No code before its ADR is Accepted (10x gate). Amendments are new ADRs or dated amendment
   sections, never silent edits.
3. **Two lanes.** Code steps: `vN/10x` and `vN/ponytail`, each in its own worktree and `CARGO_TARGET_DIR`.
   The ponytail lane gets the same prompt and the ponytail skill text verbatim (level `full`), plus
   `ponytail-review` for code or `ponytail-audit` for measurement and close steps.
   **2026-11-28 (V2):** the separate `CARGO_TARGET_DIR` per lane is not optional. Cargo's directory lock covers compiling, not
   running, and two worktrees of one crate produce identically named tool and test binaries, so a shared directory let one lane's
   test run execute the other lane's binary (two link failures and two contaminated runs in V2; both lane records). On this PC a
   lane runs cargo with `-j 2`, one command at a time, in the foreground.
4. **Comparator and cross-review.** The EM compares the two lanes hunk by hunk; each lane reviews the other's
   diff; disagreements are adjudicated in `reviews/YYYY-MM-DD-ponytail-vN.md` with reasons.
5. **Verifiers.** Two independent agents re-check the merged candidate: A for safety and privacy (keys, files
   from outside, logs, lyrics, church data), B for feasibility and correctness (numbers, budgets, citations).
   A lost lane or verifier (content filter, crash) is re-run before merge.
6. **Gates** (all must pass): the existing CI jobs; the eval gate (no metric worse than `fixtures/baseline.json`;
   the baseline is tightened, never loosened without asking); the media and private-data guard; `kit_check`;
   every named safety test the step lists; budgets (never raise a cap; stop and report).
7. **Records in `.10x/`:** `decisions/<role>/church-autoadvance.md` (what was decided and why),
   `reviews/YYYY-MM-DD-ponytail-vN.md`, `reviews/YYYY-MM-DD-vN-tickets.md`, QA and security review files on close
   steps, `status.md` (phase, numbers, founder items), `handoff.md` (the next step's brief, row table).
8. **Outward actions** (push, PR, merge, tags, issues, comments) only under the founder's batch; drafts only for
   releases (ADR-020); agents never publish.

## 3. Review rules

- Author ≠ reviewer. The owning senior approves changes to their rows; the UI consultant approves every GUI
  change; the security engineer role approves anything that touches keys, commands, files from outside the
  repo, logs, help bundles or the kit's prompts and skills.
- **Privacy on every artefact:** no lyrics, slide text, heard words, church names, song titles, host names,
  licence numbers or private paths in any PR, issue, review, log or commit; aliases only ("pilot church",
  "private song P1", "booth PC"); numbers-only eval output.
- **Evidence:** every claim cites `path:line` or a measured number; anything unchecked is marked
  [UNVERIFIED]; estimates are marked [est.].
- **Sunday freeze:** no merge to `main` and no release Friday 18:00 → Sunday 14:00 church time; a booth freeze
  around Christmas (FA-28); updates only by the operator between services (ADR-020).
- **Held-out discipline:** whoever tunes the follower never sees per-fixture held-out rows; one held-out look per
  milestone, logged.
- **Budget:** a step that would exceed its stated share of a row stops and reports; no silent row moves.

- **Two gates before autonomy (round 3 draft, FA-52; ADR-022 § 3 kept).** Gate 1: 2 scored shadow Sundays meet the
  Correct bar, then songs mode runs **with a minder at the PC**. Gate 2, later and separate, removes the person:
  ≥ 4 consecutive green Sundays, ≥ 300 scored occurrences, 0 early moves beyond the line (0.3 s on rehearsal truth,
  1.0 s live), 0 spurious presses, two volunteers passed the minder card, and Tier A only (FreeShow with read-back;
  ADR-032). Thresholds are tightened, never loosened. A song demotes to suggest-only after any manual move.
- **Commit gate for the round-3 outputs (`round2/53` § 4).** Nothing from the autonomy round is committed until the
  founder says "go" on committing them (every FA from FA-01 to FA-77 is answered as of 2026-11-27, FA-76 parked; all are recorded in `founder-action-items.md`); until then every file stays in
  `C:\dev\voxxa-strategy-staging\`. After the go, each lane commits only the files its step names, on its own branch,
  through a PR with green CI including the media guard.
- **The lane scan before any commit (`round2/53` § 4.4), verbatim:**

  **Private forever** (never in any repo, any tag, any ticket, any artifact): lyrics and setlists, every recording,
  `sessions\`, `practice\`, FreeShow show and layout ids, the FreeShow test show, raw probe replies, the API
  password or token, the repertoire inventory and its signature, the filled rota and any volunteer's name, consent
  forms, incident reports as written, `manifests\`, `reports\` (only the schema and made-up examples are public),
  `trend.csv`, the filled test cards, the lab `.py` files and their pytest, OLTW reference captures, `scan-terms.txt`.

  **The scan a lane runs before any commit** (§ 4.4). The terms live in one private file,
  `C:\dev\voxxa-church-private\scan-terms.txt`, one per line, never in the repo: the booth host name, the church name
  and its short forms, the private song title(s), the founder's Windows user name, every volunteer's and leader's name,
  the street and town, the CCLI licence number, the church's e-mail domain. The lane runs, on the staged files only:

  ```
  git diff --cached --name-only -z | xargs -0 grep -n -i -F -f C:/dev/voxxa-church-private/scan-terms.txt
  git diff --cached --name-only -z | xargs -0 grep -n -i -E '\.(wav|mp4|m4a|mp3)\b|[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[a-z]{2,}|voxxa-church-private|voxxa-private|fixtures[/\\]private|recordings[/\\]|songs[/\\]|Bearer [A-Za-z0-9]|password *[:=]|C:\\Users\\|([0-9]{1,3}\.){3}[0-9]{1,3}'
  uv run kit/tools/kit_check.py      (once V5 has merged)
  ```

  Zero hits in the first two commands, or the lane stops and reports **counts per file** (never the matched line) in
  its record. Allowed exceptions are written next to the regex in `CLAUDE.md` § "Sunday safety lines": `127.0.0.1`,
  the string `<church_root>`, the alias `<lab>`, and the three lab file names when the prompt names them. The scan
  runs on staged files only so that the two older `.10x/` files that already carry some of these strings (the
  pilot-facts line in `handoff.md` § Q9W/Q9V and the pilot-church and test-song lines in `status.md`) do not block
  every commit; whether to scrub those two files is a founder decision this layout only flags (no FA number assigned).

## 4. Agent workflows: when, how, and what they cost

- **When a scripted workflow is used:** multi-lane strategy rounds (like this one: four drafts, a ponytail
  lane, two adversarial reviews, a synthesiser) and L steps. S and M steps run as plain sessions with two lanes.
- **Authoring:** with the `workflow-authoring` skill; each agent gets the shared brief, the safety block and the
  one file it may write.
- **Cost bands** (list price, `.10x/specs/2026-11-11-prompts-10x-team.md:9`): S $3–8, M $10–25, L $25–50, ×1.5
  rework on L; a ponytail lane roughly doubles a code step; verifiers add about 20% [est.]. The V plan after round 3 (draft: 24 steps plus V3c
  conditional; V6b dropped; V13b, V5b, V5c, V16 deferred) totals ≈ $183–446 for one lane, or ≈ $350–875 with the ponytail
  lanes and verifiers [est.] (`plan.md` § 2; round 2's figure was ≈ $315–780 for 22 steps).
- **Approval rule:** the EM gives the founder the estimate before any workflow starts; anything above $50 [est.]
  needs an explicit yes; a run that reaches 1.5× its estimate stops and reports.
- **Recording:** each step's actual token use and cost go into `status.md` beside the estimate, so the bands
  can be recalibrated monthly.
- **Content filter:** agents never echo song text; a lane lost to the filter is re-run with the "slide indices
  and made-up words only" instruction.

## 5. How the founder is consulted

| When | What the founder gets | Format |
|---|---|---|
| Monday | triage: tickets, founder items due this week, last week's numbers | one message: decisions first, each with options, a recommendation and why (as `founder-action-items.md`) |
| Before each step | the pre-approval batch and the cost band | one question batch, answered once |
| ADR ready | the ADR and a 5-line summary | approve / change / reject |
| Thursday | demo: the replay table and any held-out or booth numbers | numbers only |
| Sunday | shadow or pilot run (founder at the booth) | checklist from the step |
| Monday after | debrief: numbers, step-ins, new tickets | numbers and aliases only |
| Any time | **stop rules:** a wrong-slide or privacy defect found in `main`; a cost overrun; a request that needs an outward action not pre-approved; anything touching the booth PC's installed voxxa or Presenter | immediate message, work paused |

Rules: ask before hard-to-reverse or outward actions; never re-ask a decision already recorded (brief § 2,
`handoff.md`); one numbering scheme for founder items (`FA-nn`), never reused.

## 6. Definition of done (per step)

- The ADR is Accepted and the step's acceptance criteria are met with numbers.
- Tests: new logic has tests with made-up words; the named safety tests pass; replay determinism holds.
- Budgets: inside the step's stated share; rows recorded in `scripts/loc_budget.py` with an ADR citation.
- Docs: user-facing changes in plain language; runbooks linked from the status row that needs them.
- Records: decision files, the ponytail review, tickets, `status.md`, `handoff.md` written.
- Privacy: the private-data guard and `kit_check` pass; nothing church-specific in the diff.

## 7. Recreating this team for another product or church

The kit (`kit/`) is for **setting up a church**. This process document is for **developing voxxa**; it lives in
`.10x/specs/` beside the prompt pack. A new strategy round reuses this file, `plan.md`'s prompt format and the
workflow shape in § 4, with a new brief; role prompts are written fresh from the brief, never copied from a
previous round's staging files (they carry private facts; review 20 S-45).
