# ADR-036: Re-anchor for every slides app: one position interface, three sources (output-frame hashes, a scoped key hint, read-back where it exists)

**Status:** Proposed (draft, 2026-11-27; revision 1 the same day after the lab's hash probe; founder direction and FA-77 of the same day: hashes 1, navigation-key hook 2, APIs 3) · **Feature:** church-autoadvance · **Reversibility:** Medium (one module, one row) · **Author:** 10x-Team synthesiser from the founder's direction, `research_notes/…/presentation_software_landscape.md` and the lab's `dhash_probe` numbers (system32-24, 2026-11-27)

**Revision 1 (2026-11-27).** The first draft proposed a 64-bit whole-frame hash. The lab measured it on rendered public-domain hymn slides (3 hymns, 8 full-screen and 16 lower-third slides, 1080p; small and synthetic): two distinct lower-third slides hashed identically (min pair distance 0.000), the text region at 64 bits sat at or under capture noise (0.016–0.078), and a 256-bit text-region hash with a small dead zone separated cleanly (min pair 0.066 lower / 0.121 full against noise ≤ 0.012). Decisions 3, 4, 5 and 8 and the plan's V8c are rewritten on those numbers; a booth probe (task 0) comes before any build.

## Context
- The founder's direction (2026-11-27): voxxa must re-anchor consistently and smoothly on **every presentation software on the market**, however each one works; most development effort goes here; the measures are reaction time, interoperability, interface, security, and a Unix / suckless shape: do what is needed, no bloat.
- Today re-anchor exists only where an app answers "which slide are you on?" (ADR-031 amendment 3, FA-61). From the research (as of 2026-11-26): read-back and a slide-index jump exist in FreeShow, ProPresenter 7, Holyrics, OpenLP and Quelea; EasyWorship has a command API (jump, read-back unverified); Proclaim is unverified; **WorshipTools Presenter, MediaShout 7, SongShow Plus and VideoPsalm have no API at all.** The church runs Presenter today.
- A keyboard hook that counts the operator's arrow keys was refused in round 2 as keylogger-shaped (adjudication S-14; spec § 10 risk table). The founder's FA-77 order puts it second, so it exists, scoped (Decision 5).
- Every app renders its output somewhere the booth PC produces. **Whether that output is a Windows display the PC can capture is an assumption until the booth probe says so** (Decision 9): if the Blackmagic chain takes key and fill from a DeckLink or UltraStudio card through Desktop Video, the output is not a desktop display; exclusive fullscreen can return black; desktop duplication stops on a disconnected remote session or the secure desktop.

## Decision (proposed)
1. **One interface.** `PositionSource::current() -> Option<Position { slide, t, confidence }>`, polled by dispatch, never by the follower. The follower keeps receiving `reanchor(slide, t)` (ADR-031 amendment 3) and knows no app.
2. **Source A, read-back API** (built third, FA-77) where the app has one: the per-app bindings (ADR-024, `kit/templates/bindings/*.json`) gain a `read_back` entry; the adapter is data (URL, key path, index base), not code, wherever the reply is JSON. FreeShow (V8b) is the first; ProPresenter, Holyrics, OpenLP, Quelea follow as bindings files, each verified by one probe like V3e's.
3. **Source B, output-frame hashes** (built first), for every app and as a cross-check for Source A. voxxa captures the **text region** of the slides app's output (named in the church profile; for a lower third, the bottom band) at about 10 Hz and reduces it to a **256-bit difference hash** (33 × 8 dHash over a box-resized region, with a small dead zone, τ = 3, so flat backgrounds do not flip bits under noise), 32 bytes per slide. The song's hash table is learned, never typed (Decision 6). **Match** = the nearest table entry within a threshold set between the measured capture noise and the song's smallest pairwise distance, with a margin over the second-nearest entry. A **`blank`** class, one known hash shared across songs, covers the empty output (black or key): lower thirds go blank at instrumentals and between songs, and blank is never "uncertain". Hashes live in the per-song layout file (FA-56) as numbers.
4. **Settle rule and reaction time.** Source B acts only on two consecutive frames that match the same slide with the hash stable between them. A frame that matches nothing during a transition is ignored; only a **stable** non-match sets `position_uncertain`. So the re-anchor delay is the app's transition plus about 200 ms: with FA-57's 500 ms fade about 700 ms on FreeShow; Presenter's transition time is unknown and is measured in task 0. Source A: one poll interval (100 ms) after the change. The Tight bar's "re-anchor within 300 ms" of the first draft is withdrawn; the bar is "transition + 200 ms", measured per app.
5. **Source C, a scoped key hint** (built second, FA-77). A low-level keyboard hook receives every keystroke system-wide, so the callback keeps only eight codes (Right, Left, Up, Down, PageUp, PageDown, Space, Enter) and drops everything else before it returns; it runs on its own thread and never blocks (Windows silently removes a hook whose callback exceeds `LowLevelHooksTimeout`); autorepeat of a held key is collapsed; it counts only while the slides app is the foreground window and is off when Songs is off. **A key is a hint that a change is coming, not a position:** it re-anchors only when Source B sees a changed, settled frame within latency + transition, and is dropped otherwise, so Space or Enter typed into the app's own search or edit fields never count as a move. A health-check row says "hook alive". The review file names the antivirus and trust cost the round-2 review raised, and the Security role signs the scope.
6. **Learning without poisoning.** A commanded move learns the new index's hash only when the frame changed and the follower's own evidence agrees with the new slide; otherwise the entry is stored **unconfirmed** (a missed key would otherwise store the old slide's hash under the new index). The rehearsal walk-through (V12) fills the rest and records each song's **smallest pairwise distance**; pairs under the threshold are a **collision pair** and are handed to the follower's evidence like identical text; a song with an unresolved pair gets a health-check row.
7. **Attribution window.** After voxxa commands a move, frames inside (app latency + transition + margin) that still show the old slide are not a manual move back; otherwise a slow key response re-anchors to the old slide and voxxa moves again (oscillation). The window is measured per app in V8c and stored in the bindings file.
8. **Security.** No process injection; capture reads only the named region, only while Songs is on, and keeps nothing but 256-bit numbers; no pixel, thumbnail or word is written anywhere. Capture of a display is an ordinary, user-visible OS permission. The hook's scope is Decision 5's and nothing wider.
9. **Probe before build (V8c task 0).** On the booth, numbers only: does capture see the output at all (the DeckLink question); a static slide's hash stability over 60 s; pairwise distances over one walk-through of a public-domain hymn; the transition time; the attribution window. If capture cannot see the output, Source B's capture point moves to where the output exists (a capture card's loop-through, or the app's stage/preview window) and the ADR is amended before V8c builds.
10. **Budget.** One new row, `position (src-tauri/src/position/)`, estimate 300, cap 900 under FA-54's rule; the capture uses the OS API already linked by Tauri on each platform, or one small capture crate if the Linux path needs it (ADR-005 inventory, FA-50); no OCR, no model, no new service.
11. **Tiers restated (ADR-032).** Tier A = jump + any position source; Tier B = keys-only with Source B gives a position too, so on Presenter voxxa may move from "suggests" to "moves it" once Source B passes its bar (one more FA at that time; FA-44's suggest-only stands until then).

## Alternatives Considered
| Alternative | Pros | Cons | Why not (proposed) |
|---|---|---|---|
| 64-bit whole-frame hash (first draft) | 30 lines, 8 bytes | measured: distinct lyric slides collide (0.000); text region at 64 bits is inside noise | replaced by 256-bit text-region hashing (revision 1) |
| Navigation-key hook as a position source | tiny, instant | hook-shaped (antivirus, trust); misses mouse, remote apps, pedals; counts Space/Enter in edit fields; refused once | kept as a **hint** only (Decision 5), second priority per FA-77 |
| OCR of the output | reads any app | a tesseract-class dependency; words in memory; slow on the GTX 960 PC | hashes answer the same question with numbers |
| UI Automation of the app's slide list | exact | per-app, fragile, breaks on each release | no |
| APIs only (the plan before the direction) | smallest | the church's own app has none; "every app" is the direction | no |

## Consequences
- **Positive:** one re-anchor path for every app; the follower never changes; the layout file (FA-56) becomes the single per-song record (sections, ids, hashes, min pair distance, blank).
- **Negative:** a display capture permission to explain; a rehearsal walk-through becomes a requirement for Source B songs; a changed output style (font, background, region) invalidates hashes until the next walk-through; re-anchor is bounded below by the app's transition.
- **Risks:** the capture point may not exist on this booth (Decision 9 probes first); video backgrounds move the text region's bits (hash the text band only; a `video_bg` flag per song falls back to Source A or suggest-only); two slides with identical text hash the same (collision pair → the follower's own evidence, as for repeated choruses today).
